# Error-message standards (E3)

Every message a person can see when something goes wrong: thrown errors that reach the UI or
CLI, Result `error:` strings, toasts, banners, connect / close-reason copy. The full list is
generated by `node scripts/error-inventory.mjs` into `docs/ERROR-INVENTORY.md`.
`tests/unit/error-standards.test.ts` checks the rules marked **[auto]** on every string.

## Sources
- Nielsen Norman Group, error-message guidelines and scoring rubric (visibility, communication,
  efficiency): human-readable language, precise description, constructive advice, no blame.
  <https://www.nngroup.com/articles/error-messages-scoring-rubric/>
- Microsoft, Windows error-message guidelines (Win32 UX guide, mess-error): problem + cause +
  solution, user-centred wording, no blame, "please" only when the user is inconvenienced,
  "sorry" only for serious problems, an error code only as a supplement, one message per cause.
  <https://learn.microsoft.com/windows/win32/uxguide/mess-error>; writing style
  <https://learn.microsoft.com/windows/apps/design/style/writing-style>
- Mullvad VPN desktop app strings (open source, `messages.pot`): blocking states are always said
  out loud ("Blocking internet", "Our kill switch is currently blocking your connection."),
  one cause + one fix, 5–20 words, "send a problem report" when there is no fix.
  <https://github.com/mullvad/mullvadvpn-app>
- Our own: `sentinel-solana/docs/29-UI-UX-GUIDE.md` §4–5 (close reasons, node errors), Sentinel
  SDK ERROR-MESSAGES, handshake-dvpn STANDARDS.

## Rules
1. **Say what happened, in the person's terms.** Name the thing they know (server, deposit,
   wallet, device, VPN service), not the component (RPC, gRPC, PDA, WFP, lease). **[auto: jargon list]**
2. **Say what to do next.** A message without a next step is allowed only for a plain status
   ("Disconnected."). Connect / settle / wallet errors carry an action button or a sentence that
   starts with a verb. **[auto: action or imperative sentence]**
3. **State the money.** Any failure on a path that can spend says whether anything was paid:
   "Nothing was paid." / "Your deposit is safe and will be refunded." **[auto for preflight refusals]**
4. **State the network.** Any failure on a path that can change routing, DNS or the kill switch
   says whether the internet works now, or how to get it back ("press Restore network").
5. **No raw internals.** No stack traces, no `Error:` chains, no program error names or numbers,
   no gRPC codes, no file paths of ours, no `undefined` / `null` / `[object Object]`. A raw
   detail may appear only after the plain sentence, in parentheses, and only where support
   needs it. **[auto: patterns]**
6. **No blame, no drama.** Don't say "you failed / invalid input"; say what is needed. No
   exclamation marks. "Please" only when asking someone to wait or redo work; "sorry" only for
   real loss. **[auto: "!", "please", "sorry", "invalid" as a lone verdict]**
7. **Short.** One to two sentences, ≤ 180 characters for toasts, banners and CLI errors; ≤ 300
   for a modal or a refusal that must explain money or network. **[auto]**
8. **One cause, one message.** Never one catch-all for different causes. "Something went
   wrong" is banned except as the last fallback, which must also say what to do and where the
   log is. **[auto: "Something went wrong" only in the fallback]**
9. **Sentence form.** Capital first letter, ends with a full stop (or `?` for a question);
   buttons and actions are short imperative verbs without a full stop ("Pick another server").
   **[auto]**
10. **Same word for the same thing** (glossary below). **[auto: forbidden synonyms]**
11. **Severity picks the surface.** Inline (field), toast (done / small), banner (state that
    persists: offline, kill switch blocking, leftover tunnel), modal (needs a decision, or money
    at stake). Blocking states are never only a toast.
12. **Accessible.** Banners and toasts are announced (`role="status"` / `role="alert"`), never
    colour alone, and stay until the state ends (banners) or 5 s minimum (toasts).

## Glossary (rule 10)
| Use | Not |
|---|---|
| server | node (in UI copy; CLI may say node in command names) |
| deposit | escrow, lease, position, channel (UI) |
| refund | withdraw (UI), unused balance |
| wallet | owner account |
| device | operator, device key |
| spending limit | allowance, mandate, delegate |
| VPN service | daemon, dvpnd (UI; CLI may name `dvpnd` in commands to run) |
| plan | subscription (the plan itself), provider |
| network fees | gas, lamports, rent |

## CLI specifics
- Exit codes: 0 ok, 1 error, 2 needs `--yes`, 3 usage. Usage errors print the correct usage.
- Errors go to stderr as `Error: <message>` with `→ <action>` on the next line when there is one.
- `--json` errors: `{ ok: false, error, code, action }`; `code` is stable for scripts.

## Checking it
`node scripts/error-inventory.mjs` then `npx vitest run tests/unit/error-standards.test.ts`.
The test runs `checkCopy` (`src/core/app/copy-rules.ts`) on every inventory row, with these exceptions:
- **Programmer invariants** (IPC shape checks, "not initialised" guards, builder asserts) carry
  `// copy:internal` on the throwing line: listed in the inventory, not checked. The test fails if
  more than 30 rows are internal, so it stays an exception.
- **CLI usage errors** (a synopsis, `unknown: …`, or a `--flag` message) get only rules 5 and 6.
- **"RPC"** is allowed in a message that sends the person to Settings, because the Settings
  screen labels those fields "Solana RPC" and "VPN service → RPC" (rule 10 wins).
A rule that cannot be automated (4, 11, 12) is reviewed per row in ERROR-INVENTORY during E4
and in the UI smoke screenshots.
